# Grocery Platform Development Status

## 1. Purpose

This document records the checked-out repository's verified implementation state. A model, route, or test file existing does not mean its domain behavior is complete or approved. Business decisions remain governed by `business-rules.md` and the relevant domain specifications.

## 2. Current Stage

The project has a Django modular-monolith foundation and partial identity and Shop implementation. Catalog has a single Master Category model. Most business domains remain documentation-only or empty scaffolds. No end-to-end grocery ordering workflow is implemented.

The project uses Python, Django, and DRF. `backend/config/settings.py` uses PostgreSQL when `POSTGRES_DB` is set and otherwise falls back to SQLite. A live PostgreSQL connection was not verified. JWT configuration requires `JWT_SIGNING_KEY` at startup. An `.env.example` exists; no `.env` file is included in the repository. No dotenv-loading behavior was verified.

## 4. Business Decisions and Implementation Work

The documentation records the approved MVP direction for direct Super Admin Merchant creation, one Shop at a time per Merchant, Merchant account retention and a new isolated Shop identity after Shop deletion, Super Admin Shop deactivation and permanent deletion, Super Admin Shop reactivation, variant-authoritative stock, pending-order expiry, and customer-specific Order-history access links/tokens without OTP. Analytics/retention exclusions are also documented.

Under SHOP-007, Shop lifecycle deactivation and permanent deletion were implemented as Super Admin operations with explicit confirmation safeguards for deletion. Merchant deactivation was removed from Merchant authority to prevent accidental lockout. Shop Product and Order deletion cannot be applied to absent models; inventory and Order lifecycle are unimplemented; and no customer-history access flow exists. Do not treat these documents as evidence of shipped functionality.

The Shop-deletion model and API behavior preserve Merchant credentials, and tests cover Merchant account retention and replacement Shop creation. The approved deletion authority and safeguards are exposed through the Super Admin API, but domain models for Shop Products, Orders, and Customers are absent, so related data cleanup and Customer retention are not yet implemented or verified. No customer Order-history access flow exists.

AUTH-017 documents proposed API/persistence contracts and AUTH-018 adds implementation-oriented recommendations; implementation remains pending Product Owner/Privacy, technical, and deployment approvals recorded in the authoritative design register. No runtime behavior has changed.

The Customer Order-history access security requirements are finalized in `.ai/project-context/customer-order-history-access.md`; AUTH-004 recommends a minimal global contact identity and shared uniqueness claim with Shop-specific profiles; it excludes profile, address, Order/history, credential, and authentication data from the global record. AUTH-018 separately recommends profile-rooted tenant scope, a dedicated Customer cookie/CSRF flow, and a reference-only outbox. These recommendations are not approvals. Cross-Shop identity linkage, claim ownership representation, phone normalization/backfill/collision handling, profile anonymization/number reuse, addresses, API/schema, provider, deployment, and rate-limit decisions remain open as recorded in that document's §12. Other work includes authorization for unimplemented domain APIs, Shop deletion mechanics, catalog/inventory/Order schema and stock transaction design, and notification-history retention. See the authorization matrix for policy and future tests.

Keep implementation status separate from documented product requirements and do not infer completeness from generated files.
